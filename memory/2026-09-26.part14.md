台账 07 卷31 在册 P2：`emotion_wiring_check` 的 W3b 断言的是**前端**危机不经后端
（`attempted=0`），本轮 perf 判据实测的是**服务端** `/api/emotion` 短路（`llm_used=False`）——

⇒ 命题只钉了一半：哪天 Java 侧危机开始打 LLM，前端 AC 仍绿、perf 判据会红但那是"性能"页里的红，
**验收面上读不到"危机短路坏了"**。这属既有守卫的口径扩张，不是新功能。

## 五、我这轮自己的两次失手（记账）

1. **CHANGELOG 同一段贴了两遍**：连发两条近似相同的 python 补丁脚本，两条各自 `assert count==1` 都通过
   （第一条已经插进去了，第二条锚点仍唯一）⇒ 事后 `grep -n "r40b ·"` 数出 2 个标题才发现。
   教训：**幂等补丁要在脚本里断言"目标块不存在"**（`assert "### Added（r40b" not in t`），
   而不是只断言锚点唯一——锚点唯一不能防止重复插入。
2. 一度把 `if ok:` 留着判 PASS，而 D 层的红是 `extend` 进 `problems` 的 ⇒ 会**判绿却带着 D 层红**。
   跑之前读代码发现，改成 `if not problems:`。**这条是通用形态**：新增判据汇入既有 problems 列表时，
   必须回查所有"用旧返回值判成败"的分支。
