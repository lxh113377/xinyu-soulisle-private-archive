## 五、一条行尾损伤的归因更正（我先怪了工具，实为我自己）

现象：`memory/07-next-steps.part27.md` 一度 CR=46（我写它时 CR=0），本项目钉了 `eol=lf`
⇒ 常驻判据 `eol_parity` 当场判红；已按字节还原（6 条迁移项完好）。
时间线上 `handoff.py trim-shell` 正好在那之前跑过，我据此判定是它写盘产出 CRLF，并把这条写进了
报告 / 当日日志 / GM 台账。

更正依据（两条当场取得）：
1. 同族第二例 `part29` 是 CR=3 而 LF=51 —— 只 3 行带 CR。文本模式写盘会转换**全部**行，
   所以 part29 的 CR 不是工具写的，是我在 shell heredoc 里写字节字面量（b"b"\r\n""）时
   被 Python 解释成真 CR —— 本项目已登记的「反斜杠控制字符」形态，这次由我自己复发。
2. 对 `splitvol.py` 的写入点做定向 grep（write_text 与 open(...,"w")）零命中，
   即"trim-shell 用文本模式写盘"这个机制我**没有取到**。

结论改回诚实形态：**part27 的 46 个 CR 归因未定**（候选：trim-shell 的写盘路径 / 我自己某次
读后写回 / 外部编辑器钩子）。已按"未归因"登记，并补一条待办做隔离复现：
在一个干净 LF 副本卷上单跑 trim-shell，前后各数一次 CR 与行数，只有"全部行都变 CR"才支持工具嫌疑。
教训一句：**时间相邻不等于因果**；把未归因的损伤写成别人工具的缺陷，代价是被冤枉的一方从此忽略真信号。
