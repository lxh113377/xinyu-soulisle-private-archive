## 一、起点：一条隐含前提被戳破

r35 报告写的是"逐字节对账全绿""首屏 831,152B"。本轮要复核这类主张时发现它们**只在本机成立**：
`core.autocrlf=true` + `* text=auto` 下工作树是 CRLF、仓库 blob 是 LF，
换一台 `autocrlf=input` 的机器 checkout 同一份提交，字节就变了。
⇒ 归一（108 文本文件 renormalize）+ `.gitattributes` 钉 `eol=lf` 与 binary 名单 + 常驻判据 `eol_parity`。
"归一零内容改动"用 `git diff --name-only` == `--ignore-cr-at-eol --name-only` 证明，
另建两份不同 autocrlf 的 clone 复验字节一致。

## 二、本轮最贵的一次自伤（当场还原 + 固化成判据）

首轮 renormalize 把 20 个二进制里出现的 `0D0A` 当行尾剥掉（PNG/MP4 少 1–2 字节）。
**"两侧都归一再比"的守卫看不见它** —— 两侧被同样破坏，差值为零。
处置：全部 `git show HEAD:<rel>` 还原，复核余 0 条不等；规则 **E3**（含 `0D0A` 却未声明 binary ⇒ 判红）
+ 夹具用例落进 `eol_parity_check.py`；同时**撤销我自己写严的另一半**
（"声明 binary 就必须含 0D0A" —— 那是把"本轮见过的样本"当"定义"）。
教训一句：**归一化类操作的反例必须是"内容会少的文件"，不能只有"格式不合规的文件"。**

## 三、判据接上就当轮抓到同类缺陷（"修一类不修一例"）

复跑台账 `benchmark_metrics.py` 时 `eol_parity` 立刻报
`FAIL 工作树含 CRLF：交付物/对标数据/benchmark-metrics.json`。
根因：`Path.write_text` 文本模式在 Windows 把 `\n` 翻成 `\r\n`（实测 `b'a\n'` → `b'a\r\n'`）。
枚举全部落**被跟踪文本**的写盘口并改 `write_bytes`：台账 / **补丁器 `patch_apply.py`** /
演示流水线（`timeline.json`+`subtitle.ass`）。补丁器那条最要紧：它的"写后读回复验"用 `read_text`，
universal newlines 正好把 CR 读成 `\n`，**复验步骤自己会掩盖这个缺陷** ⇒ 写与读同时改按字节；
`--selftest` 六类→八类（⑦LF 输入打完仍 LF / ⑧CRLF 输入被归一），反向证明用同平台实测的
`b'a\r\nb\r\n'`，不是嘴上说的"应该会被抓到"。
