
# 07-next-steps.part118 — 「终点」这个词的口径（r96 收尾立的规则，防下一轮再追自己尾巴）

**一手事实**：本轮我在 20 分钟内把"受理面终点"写了三次，每次写完都立刻过期——
`3d99e9d` →（补第九轮整跑）→ `9b7abce` →（落账）→ `41d2de5` →（落终点更正）→ `1583903`。
根因不是写错，是**结构性自指**：一份回执只能描述**比它自己更早**的提交，
承载这条回执的那笔提交本身永远不会被自己证明（§2.8 那条环的另一种长相）。

**定的口径（三条，写给下一轮的我，也写给读报告的人）**

1. 报告 §0 / 本卷里每一个 `sha + CI-WATCH-*` / `BATTERY:*` 都是**那个 sha 的事实**，
   **一律不解释为"本轮最终状态"**。要谈"最终"只谈**实质工作终点**。
2. r96 的实质工作终点 = **`41d2de5`**（含第九轮整跑 `BATTERY: 126/126 rc=0 ALL-GREEN`、
   `_test/settle_wait.py`、`j4_memory`/`data_rights` 的等待改造与前后实测）。
   `1583903` 及其后均为**台账/更正承载提交**，它的受理面读数由**下一轮的 `ci_status`** 负责取。
3. 下一轮入口（一条命令，不靠记性）：
   `python _test/ci_status_check.py` ⇒ 它读"最近 3 次 main push"的分类结果；
   只要它印 `CI-STATUS-PASS`，才可以把 ledger-carrier 提交并进"全绿"叙述；否则照它点名的 sha 归因。
