## 下一件：公网版只读离线壳 `sw.js`（对标反读出的差异化机会）

**依据**：r27 分母证明后 `pwa_offline=0/16` 是**真零**（实测核对 lobehub `main` 递归树 `truncated=false`、
20,740 个对象、`sw.js|service-worker.js|sw.ts` 零命中），而心屿已有 `src/manifest.webmanifest`。
⇒ 16 个同类都没做离线 SW；这是**唯一低成本的差异化能力**，且直接服务答辩场景（现场 WiFi 不稳也能演五幕叙事）。

**设计（刻意保守，只做"只读壳"）**
1. HTML 走 **network-first**（拿不到网络才回缓存）——避免"改了页面线上还是旧的"；
2. 静态资源（`js/css/vendor/data`）走 **cache-first + 版本化 cache 名**（`xinyu-v<构建号>`，改代码即换 key）；
3. `skipWaiting` + `clients.claim()`，但**只在无版本冲突时**接管；
4. **`/api/**` 一律 `network-only` 且不写缓存**（对话与情绪接口绝不能被缓存回放，否则会出现"回复重复/串号"）；
5. 公网版与本地演示版分别验证（本地 jar @8123 与 Pages 各跑一遍）。

**硬门槛：先判据，后上线**
- 本项目有前车之鉴：CloudBase 项目吃过"SW 缓存旧代码 ⇒ 后台看不到新数据"的亏（用户级记忆 [[backslash-control-chars]] 同批经验里也有"测量必带状态码"）。
- 因此必须先新增一条**时效判据**（挂在 `live_sync_check.py` 之后）：
  部署后改一个字节 → 轮询线上 → **N 秒内可见新版本**（N 定死为写进判据的常量，不许"应该很快"）；
  并断言 `/api/chat` 响应**不落缓存**（连续两次同请求可观察到差异或至少 `sw=` 标记为 bypass）。
- 若这条时效判据做不到（Pages 传播延迟本身抖动），**就不上 SW**——宁缺不糊：宁可没有离线能力，也不能让答辩现场出现"旧界面"。

**回归口径**：新增 `sw.js` 属首屏关键路径 ⇒ 必须登记 `size_budget`（新件 + 不放宽他件），
且 `public_check` 的零密钥扫描与 `deploy_sync` 三类归零都要重跑。
