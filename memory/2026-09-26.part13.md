# 2026-09-26 日志 · 卷13（r40 收口后的一条真补）

## 一、r40 的 GREEN 里藏着一个「看不见数」的缺陷

r40 push（`6d90e7c`）CI 四 job 全绿，逐 job 读 `gh run view --json conclusion,jobs` 实证，
新四条判据（`remote_tree` ±自证 / `safety_guard` ±自证 / `perf_baseline` ±自证）确实在链路里跑并回 rc=0。

但把 CI 日志 grep 出来看时发现了另一件事：`perf_baseline` 在 CI 里**只剩一句 PASS，没有数字**。

- 根因不在判据脚本（脚本 173-179 行逐项打印 min/p50/p95/max，本机看得清清楚楚），
  而在**电池的折叠规则**：`run_all_suites.py` 对每个套件只保留**最后一条**含
  `PASS|FAIL|CLEAN|UNVERIFIED|OK` 的 stdout 行 ⇒ 明细行不进 CI 日志。
- 后果是具体的：07 卷31 在册一条 P2「CI 首跑可能需重定基线」——**拿不到被检环境的 p95，
  这条待办就无法判断**，只能凭本机数字猜 Linux 共享 runner 的位置。判据是棘轮，
  棘轮不报数就等于只有一根钉死的高度，谁也不知道离顶还有多远。

## 二、修法：把数折进那一行，而不是放宽折叠规则

改 `perf_baseline_check.py` 的 PASS 行，让它自带 `实测峰值 p95 / 最紧余量 / 吞吐`
（`1c9b0c3`）。**没有**去动电池的折叠规则——那条规则是防日志爆炸的，为一个判据开例外会把
50 个套件的日志体量交出去。**可迁移口径**：在"只保留末行"的聚合器里，判据的**数字必须长在
判据词那一行上**，否则 CI 侧的观测量退化成布尔值。

本机复跑（`--reps 25`，取证 21:2x，对应 commit `1c9b0c3` 落在 21:30）：峰值 p95 **26.2ms**、最紧余量 **374ms**、吞吐 **2026.9 rps**，
`llm_used=False`（危机短路口径成立），`--selftest` 六向仍 PASS。
⇒ 400ms 阈值确实有 ~15 倍余量，此前文档写的"余量 15–25x"与实测一致（不是估计）。

## 三、这一条的登记价值

同族形态本项目已登记过一次：**判据跑绿 ≠ 判据说了话**。上一次是「门禁有没有接线」（grep 脚本路径
而非 npm 别名），这次是接线了、也绿了，但**输出被自己搭的聚合层削成一个布尔**。
归因动作也一样：先看命令的**实际产物全文**（CI 日志原文），而不是只看结论行。

## 四、闭环：CI 侧首跑数字到手，顺带推翻了一个隐含假设

`df6c813` / run `36245610695` 四 job 全 success，`gh run view --log` grep 到：

```text
perf_baseline rc=0 | PERF-BASELINE-PASS（4 个目标在预算内｜实测峰值 p95=3.3ms，
最紧余量 397ms｜吞吐 1178.6 rps｜…）
```

- 07 卷31 那条 P2「CI 首跑可能要重定基线」⇒ **关闭，且是靠数字关的**：CI 侧 p95 余量 ~120×、
  吞吐余量 ~23×，不需要动阈值，也没出现要靠抬 timeout 掩盖的红。

  吞吐却只有本机的 ~0.58× ⇒ "换环境大概差不多"这个隐含假设不成立，
  已把"禁跨环境引用绝对值"写进 `06-constraints.md` 性能口径红线。
