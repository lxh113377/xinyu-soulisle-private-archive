## 二b、事务那条：从结构回执补到行为回执（本轮做完）

原先 `clear()` 的 `@Transactional(rollbackFor=Exception.class)` **只有结构证据**
（H7 断言注解在位 + 摘注解即红的变异腿），「第二张表失败时第一张表必须回滚」这个
**行为**一次都没被证实过。原因是 Spring 事务经代理生效，而 `MemoryServiceTest` 直接
`new service` + 两个假 mapper，那条路径上根本没有容器。

现由 `server/src/test/java/com/xinyu/soulisle/service/MemoryServiceTransactionTest` 补上两条腿：

- **回滚腿**：`@MockBean ChatMessageMapper` 只投毒第二张表（`delete` 抛异常），第一张表走真 H2 真 SQL；
  断言 `emotion_record` 仍为 2 行。
- **正向对照腿**（缺它则回滚腿可以是假）：同样投毒点撤掉，断言第一张表**真被删到 0**
  —— 否则「回滚后还是 2 行」可能只是「删除从来没执行」。这是本仓「判据两侧都要取」
  与 ②-b「反例必须落在被保护分支上」在同一族上的第四次实踩。

变异腿实测（干净 worktree，`-Dtest` 只跑回滚腿）：删掉那一行注解后


## 三、索引设计与查询语句（结论：现状即正确 —— 现已有测量背书，不再只是论证）

三条取数路径逐一比对索引：`eq(session_id)+ORDER BY id DESC LIMIT` 与 `countBySessionId`
走 `idx_*_session (session_id, id)` 前缀；`recentMessages` 的 `ORDER BY id DESC LIMIT` 走主键。
无按 `emotion`/`created_at` 的过滤路径 ⇒ 不为其建索引（无消费者的索引是写放大不是优化）。
`VARCHAR(64)` 进索引在 utf8mb4 下 64×4=256 B，远低于 InnoDB 3072 B 上限，无需前缀索引。

上面这段原本是**纯论证**（读 DDL + 读查询形态），本节初稿就此收口了。
按「不量就没有资格说够」补了 `_test/mysql_load_probe.py`，本机 MySQL 8.4.9 实测：

| 量 | 有索引（迁移产物原样建） | 对照（机械摘掉那行 `KEY`） |
|---|---|---|
| 执行计划 | `type=ref` `key=idx_lp_indexed_session` `extra=Backward index scan` | `type=index` `possible_keys=NULL`（退化成主键全扫） |
| 单查询净耗时 | **0.759 ms** | **12.4 ms**（16× 差距；净耗时靠两点求斜率消掉 ~27ms 客户端启动常数） |
| 物理面 | `INDEX_LENGTH=16384` | `INDEX_LENGTH=0`（第二通道，不看计划也认得出这张表没索引） |
| 结果集 | 200 行 `sha256=d93c…` | 同一 sha256 ⇒ 索引只改访问路径，没改语义 |
| 并发 | 12 客户端 × 15 次 = 180 次，0.81 s，qps 222，错误 0，每客户端各 200 行 | — |

夹具规模 6 万行 × 2 表（200 会话 × 300 条），两表逐字节同一批数据。
两条一手坑进件内注释：① `mysql -e` 不带库名 ⇒ `ERROR 1046 No database selected`；
② 批量 INSERT 走 `-e` 参数顶穿 Windows 32 KB 命令行上限（`[WinError 206] 文件名或扩展名太长`）⇒ 改 stdin。
另一条判据缺陷也是被实测抓出来的：第一版 `L5` 用 `CURRENT_TIMESTAMP` 播种，两侧摘要必然不等，
红因与索引毫无关系 —— 正解是把夹具改成确定性时间戳（可比），而不是放宽断言（`TIMESTAMPADD(SECOND,i,…)`）。
`--negative-control` 那条腿（真优化器的有索引计划塞进对照位 ⇒ 必须只红在 L2）第一次跑时
我自己的期望「恰好 1 条红」被实测否证（真红 2 条，两个子判据同时打翻）⇒ 期望改成
「红且红因全部落在 L2」，这与全局教训「变异期望须由被测对象自报」同形。

高并发那条的**边界**：本件量的是库面（12 条并发连接 < 池上限 16，池面由
`mysql_degradation_check` 的运行时回执负责）。真·高并发（连接打满池、排队、504）
在这张两张表的演示形态下量不出来，也不该拿它当"已验证支撑高并发"。

- 直接原因：本文件当时是**未跟踪新件**，`git commit --only -- <path>` 对未跟踪路径直接报

  而共享 index 里此刻另有并行会话 staged 的上述 4 件 ⇒ 普通 commit 把它们一起收走。
- 为什么**不 revert**：revert 会删掉别人的内容（本仓既有纪律：归属失真时只做留名更正，不做回滚）。
  4 个文件的内容都在，只是记在我的提交名下。
- 与前一条（`ade8bb8` 空提交）同根：**共享 index 上"我 add 了什么"与"index 里有什么"是两件事**。
  正解次序应当是：未跟踪新件先 `git add <我的路径>` → 断言 `git diff --cached --name-only`
  **恰好等于**我的路径集合 → 不等就**不提交**，把多出的条目 `git restore --staged` 交还对方
  （或改用 `git commit-tree` 的只读临时 index 路径，本轮另两次提交就是这么做的）。
  本轮我在前 5 次提交里都做了这个断言并在说明里写明，却在第 6 次因为"新文件不能 --only"而漏掉。
