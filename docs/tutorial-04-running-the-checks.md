# 教程 04 · 跑判据（这个项目怎么做到"说绿就真绿"）

> 面向两类人：**第一次接手这个仓的人**（想知道改完该跑什么），
> 和**想质疑"你凭什么说绿"的人**（想知道每条主张能复算成什么命令）。
> 完整清单在 [`quality-gates.md`](quality-gates.md)（那份是被判据本身盯着的：漏登记会红）。

## 1. 三态：PASS / FAIL / UNVERIFIED 不是一句口号

所有自研判据共用同一套退出码约定：

| rc | 含义 | 为什么必须有第三态 |
|---|---|---|
| 0 | PASS：取到数且达标 | — |
| 1 | FAIL：取到数且不达标 | — |
| 2 | UNVERIFIED：**没取到数**（环境缺件、取数面读不动、分母为空） | 把"看不见"折成 0 或折成"通过"，是全仓最容易造的假绿 |

一条硬规矩：**没量到 ≠ 达标**。例如实测中"没有文档"和"我扫不到文档"必须长得不一样
（`peer_docs_probe` 的失明优先级就是这么写的：树被截断 ⇒ 结论一律 unverified，不许写 none）。

## 2. 改完之后至少跑这些

```bash
python _test/run_all_suites.py --exclude-llm     # 全量电池（不含真实 LLM 调用），提交/推送前的前置
python _test/repo_config_check.py                # 文档面/清单面的自洽（下面 §3 那几条都在这）
python _test/java_test_guard.py                  # Java 用例数下限 + CI 不许带 -DskipTests
node _test/emotion_eval.js                       # 情绪评测（JS 侧）
```

条数别手抄：`python _test/run_all_suites.py --list` 会自报当前套件数；
README 里那句「全量电池（N 套件）」由 `_test/suite_count_sync.py --apply` 与代码现读值对齐
（这条数字历史上**手抄过期过两次**，所以改成一条命令而不是靠记性）。

## 3. `repo_config_check` 里几条容易忽略的门

| 门 | 咬什么 | 一手事故 |
|---|---|---|
| **G4** | 电池 `SUITES` 条数 == README 声称数 | r123 我写下 157，他人加两条套件后它自己过期了 |
| **G8** | 评测集**声称条数 == 实际条数**，且工作树面与受理面（HEAD）各判一次 | 别人 clone 到 HEAD 时读到的是另一份条数 |
| **G12** | `git tag == pom == 文档「当前版本」` 三源同源 | 发版链断在中间时它必红，绕不过 |
| **G16** | 电池 ⇄ quality-gates ⇄ git index ⇄ CI 接线 **四面双向**对账 | "在电池里跑却没进文档"、"文档引了个没入库的脚本"都算红 |
| **G19** | `docs/` 真实文件 ⇄ `docs/README.md` 索引双向对账 | 幽灵引文（索引链了个不存在的文件）也算红 |

## 4. 判据自己也要有反例（否则它只是在念口号）

本仓的规矩是：**新写一条尺，必须同时给它一个"会红"的证据**，形态有三类：

1. **变异腿**：定向破坏被测对象，对应结论必须翻红。
   例：`node _test/js_engine_mut.mjs` 对表情引擎做 5 类破坏，每条都必须让对应用例翻红，
   同时**不破坏时的对照组必须全绿**——只测"会红"会放过恒绿，只测"全绿"会放过假绿。
2. **正例腿**：合法输入必须判绿。
   例：`ci_contract_check` 第一版把成员判断写错，14 条合法 blocking 全被误报"没人跑"，只有正例腿抓得到。
3. **演习腿**：阻断型判据要能强制注入红。
   例：覆盖率门 `BRANCH ≥ 0.90` 的验牙是"临时把阈值改 0.99 ⇒ 必须 rc=1 且红因点名实际比例"，改回后按字节还原。

台账侧同理：`_test/ledger_shape_check.py` 扫**全部 53 个 json 台账族**，
把"件里有 NA 痕迹却没声明"点名为红；龄期尺 `ledger_age_check` 只扫 `peer-*.json`（18 族）。
分母换面之后才发现：**不在任何尺的取数面里的 35 族，犯了同一个形状错也不会红**
（r122 那颗雷正是靠"恰好在册"才被抓到的）。

## 5. 三条最容易踩的执行坑（Windows + 中文路径）

- **`git status` 会说"干净"而字节确实不同**：本仓配了内容过滤器/EOL 归一，一手实测某件与 HEAD 差 24 加 14 删行却报干净。
  动手前先跑 `python _test/eol_parity_check.py`，在它的红项里查你要动的那个路径——
  它的红因之一就是「工作树字节 != blob 字节（且该文件没有待提交改动）」，这正是"看不见自己在改什么"的形态。
  别为此另造一条"比字节闸"：**同一事实只许一处判**，重复的尺早晚和原尺分叉。
- **管道会吃掉退出码**：`python x.py | tail -3` 之后 `$?` 是 `tail` 的。要 rc 就用 `${PIPESTATUS[0]}`。
- **列文件的参数别混用**：`git ls-tree -r --name-only -l` 里 `--name-only` 会把 size 列一起吞掉，
  解析结果为空 ⇒ "查不到文档"被读成"没有文档"。
- **反引号别走 bash 内联**：写进 `python -c "..."` 的反引号会被 shell 当场求值，把命令文本吃掉。
  本文档里的中文引用统一用「」就是为了避这个坑。

## 6. 想加一条自己的判据？

1. 件放 `_test/`，退出码守 §1 三态；
2. 进 `_test/run_all_suites.py` 的 `SUITES`；
3. 在 [`quality-gates.md`](quality-gates.md) 登记（否则 G16 红）；
4. 跑 `python _test/suite_count_sync.py --apply` 把 README 的数字对齐（不手抄）；
5. 补 §4 的反例腿，并**当场演一次红**。
