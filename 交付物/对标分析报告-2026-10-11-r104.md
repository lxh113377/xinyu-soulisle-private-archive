## 2. 逐项差距与一手发现（全部可复算）

### 2.1 整跑电池被一个慢判据熔断（P0，维度 3/4）

r101 收口时整跑还能出 `BATTERY:` 行；本轮首跑**连收口行都没有**。归因链（一手复现）：

```
python -u -B _test/run_all_suites.py --exclude-llm
  → subprocess.TimeoutExpired: '_test/eol_parity_check.py' timed out after 600 seconds
  → Traceback 一路逃出 main() ⇒ 电池 rc=1、无 BATTERY 行、该套件之后**一套都没跑**
```

`eol_parity` 单独跑 **140.4s**（本机空载）：它对每个被跟踪文件 spawn 两个 git 子进程
（`check-attr binary` + `show :path`），730 个跟踪文件 ≈ 1400 次 spawn。并下载体下
（并发会话同时在跑）spawn 成本被放大约 4 倍 ⇒ 突破 600s 硬顶。

**"受理面断续"比"一套件红"更坏**：既不知道哪些绿，也不知道哪些红，下一轮连从哪继续都不知道。

### 2.2 peers 侧 6 天旧照 + 5 仓 blind（P1，维度 1/6/7）

- SNAP `ts=2026-10-04 18:23`（r95 所采）⇒ r101 报告的 peers 列只能写"沿用"，"现测"二字名不副实。
- `peer-community` 族 **5/16 仓行为面 403**，且**三轮采集固定同样 5 仓**（Open-LLM-VTuber / MASCOT /
  Mental-health-Chatbot / opensoul / ryza-ai-revive）——固定失败集合不是随机限流，是结构性问题。
- 根因（读码 + 单发对照实验定死）：`probe_repo()` 的 peers 路径还在打
  `search/issues?q=repo:X+author:app/dependabot`，而 docstring 与 JSON 的
  `behavior_endpoint` 字段**声称** search 已弃用、改用 `/pulls`——那个修复只落在 self 半边，从没落到 peers。
  search 端点受 secondary rate limit 影响，同一请求单发与 `/pulls` 形态实测均 200 ⇒ 不是权限、是端点选错。

### 2.3 件内 NA 与顶层声明分叉（P1，维度 1/7）

`peer-memory-2026-10-08.json` 顶层 `blind=0 / na=[]`，件内 `repos[*].edge` 却有 **5 处 `"NA(`**。
r101 用**带 expiry 的豁免**压住（到期条件 = 探针把字段级 NA 计入声明位 + 下次错峰真采）。
豁免是"有人认领的余量"，不是修好——本轮把它销掉。

### 2.4 耦合尺棘轮红 + 一条错判的旧账（P1，维度 3）

现读 `C1=29 > 基线 22`，红因有二：

- r87 的 `face_check.py` 新进 **7 处** `wait_for_timeout`，全部**未登记评审结论**（尺子在喊"没人看过这些"）；
- r101 把 `j4_memory_check.py::page.wait_for_timeout(10000)` 登记为 debt-open，理由写"等服务端写入，
  可改轮询 /api/memory/stats 计数到位"——**这条登记是错的**：B 腿（`cfg.remote` 缺省=关）是**阴性对照**，
  remote 关着时服务端计数恒等于基线 ⇒ 轮询"计数到位"永不满足、轮询"静止"立即满足（窗口消失）。
  **确认一件事没有发生，没有完成态可等。** 本轮改判 `unobservable` 并写明更正理由。

### 2.5 一次我自己犯的错（记下来因为它差点骗过我）

`settle_wait.wait_reply` 上收时，我把 `mark_last` 放在 click **之后**。离线模板 ~15ms 回完 ⇒
标记打到**本轮新产生的终态气泡**上 ⇒ 谓词永久不成立 ⇒ emotion_wiring W3b 危机腿 30s 超时，
`storage_resilience` 五个用例全部 8s 超时。现场极具误导性：`n` 已 +2、`data-emotion` 已就位、
`pendingTurns` 归零——**判据崩在一个本来是对的谓词上**。

同类还犯了一次：`storage_resilience` 的 `mem_before` 取样点放在 `settle(count>0)` **之后**，
取到"1"之后等 `!== 1` 永不成立（本轮只记 1 条）。

两条都修完并各留注释说明"为什么必须在这个位置"。**教训**：完成态等待的正确性不只在谓词，
还在**取旧值/打标记的时序点**——这一层没有任何现成判据能替你看。

   上收前它在 `ux_guards_check` 与各判据里被抄了 5 份；r101 的同族教训（gh_cred 三处抄一份）
   就是为这个立的。**改它之前先读 §2.5。**
2. **`eol_parity` 的批处理三件套**（`_parse_check_attr_z` / `_parse_cat_file` / `check_attr_binary`）——
   纯函数分离，selftest 能喂合成字节流（含敌意内容与截断），判据语义零改动地拿到 4.6× 提速。
   **任何"逐文件 spawn 一个 git"的判据都该照这个形状改。**
