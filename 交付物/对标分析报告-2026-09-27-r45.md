三条结论，其中两条是撤回我自己的话：

1. **撤回①**："0.56 天全池最优／11 家里第一" 是假主张 —— 真实第三。已在报告与台账逐处改口（5 处）。
2. **撤回②**：我随后又把它解释成"前两名是 `pushed_at +08:00` 对 `published_at UTC` 的时区残差"。
   拿原始字段一比就崩：leemo `pushed=2026-08-27T21:18:40Z / published=21:20:27Z`（推送后 **107 秒**发布）、
   ryza 两侧同秒 ⇒ **那是真快，不是假象**。带 `+08:00` 的只有我自己那一行（本机 git 输出的本地偏移），
   且它参与计算时偏移已被正确解析（`09:19:30+08:00` = `01:19:30Z`，与 published 差 13h22m = 0.557 天 ✓）。
   ⇒ 教训：给指标找"它是假的"这种解释之前，先把被解释对象的原始字段打出来看。
3. **仍然成立的结构性缺陷**：`lag = pushed_at − published_at` 只量"两端之间的时间"，
   在高频提交的项目上会**严重低估**未发布量 —— 我这 0.56 天里塞了 **44 个 commit / 11 个 feat**
   （✅ `git log --date` 实测跨度 09-26 20:12 → 09-27 09:56，共 13.7 小时；

   ⇒ 所以 R1 用 **feat 计数**做阻断、R4 用天数只做报告，这个分工是被这条数据逼出来的，不是先验设计。

## 2. 逐项差距说明

1. **高｜切版没有触发条件，只有记忆**。11 个 feat / 44 个 commit 堆在 `[Unreleased]`，时间跨度 13.7 小时
   （✅ `git log --date=format` 首末提交 09-26 20:12 → 09-27 09:56）。对手里可对标的正例是 `lobehub`：
   同样高频提交，但它的 tag 序列密到 lag=6.46 天且 release 带 20 个资产 —— **区别不在忙不忙，在有没有"攒够就切"的动作**。
   v1.4.3 之后的 r39/r40a-d/r41/r42/r43/r44/r45 **零切版**（11 个 feat 全部压在 [Unreleased]），而这期间对外文档一直在写"部署包已就绪"。
   ⇒ 触发条件必须由**计数**（R1）给，不能由**天数**（R4）给：13.7 小时这种跨度，天数指标完全无痛。
2. **高｜CHANGELOG 覆盖率没人量**。实测 `[Unreleased]` 的 20 条 bullet 全是 r39/r40* 的，
   **r41（in-build 单测 0→30 用例）、r42（无障碍常驻门禁）、r43（干净克隆可跑性）三轮 feat 级提交一条没记**；
   r44 只在 r45 那条"修 r44 造成的红"里被顺带提过 ✅ 复算见 §3。
   ⇒ 一个只看 bullet 计数的判据会被存量掩盖成"通过"，这条是本轮判据自己的第一号缺陷。
3. **中｜发布资产与 CI 结论无绑定**。v1.4.3 之前每次发版都没有"发出去的这份恰好是 CI 验过的那份"的证据链。
4. **中｜发布自动化仍是手工**（台账 part28 第 6 行登记为 P2，至今未闭合）：本轮又手敲了一遍 mvn/zip/tag/gh，
   手敲就有漏步骤的风险 —— 上一轮的漏 `PRECACHE` 就是同一族。
5. **低｜滞后指标口径误导**：`lag` 首版按整数天截断，把 22 小时前的发布读成 `lag=0`（假新鲜）。
   已改小数天并补专用用例（✅ `RELEASE-GOV-SELFTEST: 12/12` 含"30 小时=1.25"用例）。
