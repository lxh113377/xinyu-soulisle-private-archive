## 2. 逐项差距说明（量化）

- **功能 G1 向量长记忆 0 vs 7/16**：letta/SillyTavern 系标配 RAG/向量检索；self 只有两表（chat_message/emotion_record）+ 73 条词表。差距=语义召回能力缺失。借鉴：先文档化 MemoryService 扩展缝，再评估 pgvector/嵌入侧车（Java 调 Python 侧服务，不硬啃）。
- **功能 G2 流式输出 0 vs 2/16（盲区另计）**：lobehub 系 SSE 逐字；self 为整包回传。差距=长回复体感延迟。借鉴：`LlmProxy` 已透传上游，追加 `text/event-stream` 为增量能力（本轮不做，排 P1）。
- **功能 G3 多语 i18n 0 vs 3/16**：出海/评审英文面弱。借鉴：README.en 已有，先补关键 UI 字符串表（P2）。
- **架构 G4 无构建校验**：零构建=零类型门；peers 用 lint/typecheck 拦人。差距=重构安全网只有测试。借鉴：已用双覆盖率门弥补，增量加 `node --check` 语法门即可（P2）。
- **性能 G5 无 CI 性能门、无公开数字**：与全行业同病（0/16 公开数字）。差距不是落后而是共同缺失；self 已有本地棘轮，本轮补 PERF 基线文档把"自证"变成"可引用的数"。
- **扩展 G6 有机制无文档**：词表 SSOT、LLM 可换、memory 开关、双部署目标全部无统一扩展手册。第三方集成能力不可发现=等于没有。本轮补 EXTENSIONS.md。
- **维护 G7 社区面缺 3 件**：CODEOWNERS/conduct/support 无；peers 头部 lobehub 三者全有。差距=外部贡献者进入路径弱。评级低（单团队参赛项目，按需补）。
- **文档 G8 机读强人阅读弱**：openapi.yaml 11 路径无手册版；benchmark 显示 readme_thorough 仅 6/16 有，self README 18k 字符已达标，但 API 手册缺。本轮补 API.md。
