## 2. 逐项差距说明（自家运行时，判据 `_test/context_budget_check.py`）

取数面 = 拦 `/api/chat` 读 `request.post_data`，反解出 system 段与 messages 条数（真流量出口）。
截断条数由**判据自己**用「发该轮之前本机 history 条数 − 窗口」算出，不采信产品报的数
（`measure()` 自比是登记在册的假反例形态）。

| # | 判据 | 修前实测 ✅ | 修后 ✅ |
|---|---|---|---|
| X1 | 历史覆盖率（送进模型 / 本机已积累），棘轮下限 0.30 | 14 轮：**10/26 = 0.385** | 0.385（窗口不变，见下方"读法"） |
| X2 | 被截掉的条数必须由概要注意送达，**且条数对得上** | `CTXBUDGET-FAIL: X2 截断了 16 条历史，但 system 里没有「早前对话概要」段` | 概要送达且 `此前 16 条` 与独立算出的 16 一致 |
| X3 | system 段字符上限 1,600（persona+策略+记忆+概要） | 357（无概要注意） | 357 → 实测仍 ≤ 上限；**首次给"注入更多上下文"这件事设了预算** |
| X4 | 反向腿：零截断 / 首轮**都不得**出现概要注意 | 概不存在，天然不红（等于没测） | 概要注意在 drop=0 时必须不出现；判据有反例③钉住 |
| X5 | 隐私：概要注意与记忆段内不得出现任何用户原话 | 不适用 | 原话泄漏 **0 条**（概要只写情绪标签与计数） |
| X6 | 未捕获异常 | —— | 0 条 |

**覆盖率为什么"没提升"是诚实的**：本轮做的是**表示层补偿**（让模型知道"前面还有 16 条，
主要是焦虑×6、低落×4，危机 0 次"），不是把原文再塞回 prompt——后者同时撞 r52 的 R7 隐私口径
与 X3 成本上限。⇒ 报告禁止把它写成"上下文能力提升 X%"；能写的只有"截断损失从 100% 无补偿
变成有结构化补偿"，且这个变化由 X2 判据（修前真判红）钉住。

**差距的本质**（与 r52 同族）：这一格此前**连一个数都没有**。十四份报告的"性能表现"量的是首屏与
包体，"可扩展性"量的是故障态，没人量过**对话变长之后模型看见多少**。所以真正的产出不是那 16 条
被补上了，而是它从此变成一个会红的判据：将来谁把 `HISTORY_MAX` 改小、或把概要注意悄悄改成常量，
`context_budget` 都会当场抓住。
