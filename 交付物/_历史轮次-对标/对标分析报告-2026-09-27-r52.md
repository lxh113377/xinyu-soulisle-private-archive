## 3. 本轮顺手收掉的 r51 挂账（两项）

**3-1 中优先：README 面向使用者排障段**（r51 §4 列了未做，就地蒸发一轮）
补了「三种真实状态 + 你可以做什么」表，并立刻用 `_test/readme_troubleshooting_check.py` **双向**钉住。
首跑该判据抓到两处我自己的错（见 §4-1），这不是"文档写完了"，是"文档被产品按回去"。

**3-2 P1-2：挂起型 30.2 s 里未归因的那 ~15 s**（r51 明写"未归因不得写成机制"）
- 根因不在产品，在**夹具的计数单位**：黑洞服务器原先按 `accept` 次数记 hit，keep-alive 下两条串行
  请求复用同一连接 ⇒ 记成 1 次，于是"1 条请求怎么会花 30 s"看起来无解。
- 改成数 `POST ` 出现次数 + 页面内 `fetch` 打时刻戳，当场看见：**2 条腿，间隔 15.0 s**。
  即 classify 腿吃满一个 15 s 熔断 → 词典兜底 → reply 腿再吃满 15 s ⇒ 串行相加 30.0 s／实测 30.2 s。
- 处置：分类腿只回 ~20 token 的 JSON，15 s 是"等回答"的预算不是"等首包"的预算 ⇒ 单独给 **6 s**
  （DeepSeek 正常分类 <2 s，仍留 3 倍余量）。整轮 **30.2 s → 21.3 s**（−29.5%）。
- 判据面：`HANG_BUDGET_S` 35 → **25**（同一把尺：实测上界 + 17% 余量）；并新增 **F4b**——
  兜底耗时超过单腿预算 1.5 倍却只观测到 1 条 fetch ⇒ 判红"未归因"，本判据从此拒收未归因的解释。

**3-3 P1-1：heredoc/引号族机器化** —— 做了一半，另一半**主动撤销并写下理由**：
- ✅ Python 腿进了 G9：`repo_config_check` 现在要求每个 `_test/*.py` **解析得动**。
  真正的洞不是"没这条判据"，而是 `third_party_imports()` 对 `SyntaxError` 是 `except: continue`
  ⇒ 被写坏的文件在依赖审计里**直接隐身**。
- ⛔ Java 腿（逐行引号奇偶）实测**误报 6/20** 后撤出判定集合，函数留作手工诊断。理由写在 docstring 里：
  文本启发式重造 Java 词法器不成立，而该事实的**权威判据是 javac**，java-build 在 CI 链上、
  T4 又盯住构建步不得加 `-DskipTests` ⇒ 同一事实不另立一把更差的尺。
- 附带修掉两处"判据自己坏掉长得像被测对象坏掉"：selftest 里用了不存在的计数器（`UnboundLocalError`），
  以及**失败出口对 tuple 调 `f.split()`** —— 真有判据红时它会先崩，把红因盖掉。

   在 `fault_injection_check` 加一类"保留 emotionRemote 的挂起注入"，而不是把结论外推。
4. 真机（iOS Safari / Android Chrome）复跑故障注入与召回（r51 §4 低优先项，仍 ⬜）。
