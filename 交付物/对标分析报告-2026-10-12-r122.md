## 3. 逐项差距说明（只写本轮有新证据的）

### 3.1 文档维：整个池子只有 1 家把 API 规范放进仓库，而我们缺的是"独立教程文件"

一手台账（`交付物/对标数据/peer-docs-2026-10-12.json`，`python _test/peer_docs_probe.py --json …`）：

| 位 | peers 在册 | 我们（同尺） | 判读 |
|---|---|---|---|
| API 规范（openapi/swagger/proto/graphql） | **1/16**（lobehub） | ✅ 有 `docs/openapi.yaml`，且 11 paths ⇄ 11 Java 映射（差 0） | **这是我们的真实优势位**，且优势可复算，不是自我声明 |
| 使用教程（quickstart/tutorial/how-to/handbook… 命名文件） | 9/16 | ❌ 0 | **本轮测出的真差距**：我们的入门内容写在 `docs/README.md` 的「快速开始」一章里 |
| 贡献指南 | 10/16 | ✅ `CONTRIBUTING.md`（r120 补齐） | 持平主流 |
| 独立文档区（docs/documentation/book/wiki） | 10/16 | ✅ `docs/` 7 篇 md | 持平主流 |
| README 厚度 | min 267B／中位 9680B／max 39200B | 21542B（≈池中位 2.2 倍） | 高于中位 |

⇒ 结论改写的方向很明确：**第 7 维我们不是落后方**（3/4 高于 14/16 个对手），
唯一被机器照出来的缺口是"没有独立教程文件"——这是本轮探针**第一次**让这个差距可见。
口径诚实性的另一半（必须写）：
- 本尺只看**本仓 git tree**。SillyTavern 判 1/4（README 只有 267B）不代表它没文档——它的正文在**站外**（docs.sillytavern.org）。
  ⇒ 该位为 0 只等于"不在本仓 tree 里"，不等于"没有文档"。跨仓/站外的文档面本轮**没量**，是已知盲区。
- 教程位按**文件名**判，self 与 peers 共用同一把 `classify_docs`。我可以给本仓开例外（"docs/README.md 里那章就是教程"）
  把 3/4 涂成 4/4——**本轮明确拒绝这么做**，并在代码里写下拒绝理由：口径特例撑出来的满分会把真差距抹平。

### 3.2 性能维：老大点名的三块，此前只量了两块半

维度原文是「响应时间、资源占用率及并发处理能力」。改前：p95（响应时间）✅、rps（并发）✅（r121 打到词典引擎真实路径）、
**资源占用率❌从来没读数**——不是量了达标，是没人量过（和第 4 维 peers 那个 NA 同一种病）。

本轮补法与一手实测（spare 实例：TEMP 副本 jar `a145cbd5`、端口 8147、独立 H2、pid 3560，**未打他人 8123**）：

- 取数面＝**被测进程自己的计数器**（端口反查 pid，不是"随便挑一个 java"）：
  Windows `Get-NetTCPConnection` + `Get-Process`；Linux/CI 走 `/proc/<pid>/cmdline` 找 jar + `VmRSS`/`VmHWM` + `utime+stime`。
- 五轮读数：工作集 240.8 / 259.0 / 262.2 / 272.6 / 286.0 MB，峰值工作集恒 **333.8 MB**；
  单请求 CPU 2278.1 / 3092.7 / 2115.6 / 2278.1 / **651.0** µs。
- 阈值由这组实测推导，**不贴读数**：`MAX_RSS_MB=1200`（≈峰值 3.6x）、`MAX_US_CPU_PER_REQ=12000`（≈最坏 3.9x）。
- ⚠️ 诚实的另一半：单请求 CPU 的窗口里 **JIT、GC、H2 后台线程都算在内**，五轮跨 **4.7 倍**（同机同进程同 jar）。
  ⇒ 这条只能当"数量级塌方探测"，**禁止**写成"我们每请求只用 2.3ms CPU"这类对外结论。
  要收紧它得先解决窗口归属（只数请求线程的 CPU），那是下一轮的事。
- 取不到读数 ⇒ `PERF-RESOURCE-UNVERIFIED` **rc=2**（既不判红也不判绿）；判定与 main 共用 `resource_state()` 一把尺。

### 3.3 NA 不是终点：这轮开始验"补法本身是不是活的"

表里的 NA-DECLARED 是"诚实的空格"，但**空格里的补法命令没人核过**。
死链的 NA 比没有补法更坏——它长得像"照这句跑一下就补上了"，实际跑起来 `file not found`，
下一轮就继续抄 NA，而且抄得更心安理得。本轮装 `remedy_audit()`：

- 只判 NA 格（普通格的 source 里常有历史描述，一起判＝拦正常人改表，爆炸半径超过断言范围）；
- 工作树与 HEAD **两面分别判**：两侧都没有 ⇒ **死链判红**；只在盘上没入库 ⇒ **点名不判红**（那是别人的中间态，红会砸错人）；
- 写了"补法"却没点到具体脚本（占位符）⇒ 点名。
- 现表读数：`补法死链 0｜补法待接 0`；演习（把 `peer_issue_response_probe.py` 改成 `..._TYPO.py`）当场翻红并点名到维/格/脚本。

### 3.4 实现方式维：表情引擎的"离线面"此前只覆盖纯函数

改前 26 条表情用例全部打在纯函数层（`read`/`smileKind`/`assessQuality`），而 `window.FaceEngine` 导出的
`capability` / `enabled` / `setEnabled` / `labelOf` / `reasonText` / `cueRegions` **一条离线腿都没有**——
它们只由 `face_check.py` 的浏览器腿覆盖，而浏览器腿按 r112 口径**不进 CI 受理面**。
⇒ 「摄像头关了就真停了」「拒绝后界面不空白」这两句承诺，构建期是没人验的。本轮补 5 条，并用变异探针自证：
5 类变异（摘掉 insecure 分支 / setEnabled 改写成写 `on` / reasonText 回空串 / cueRegions 用原始值当权重 /
摘掉 RULES.labels 那一跳）**各自翻红**，对照组全绿 ⇒ `MUT-PROBE-PASS`。

顺带测出两条在册事实（不是 bug，是配置面）：`RULES.cues` 引用的 38 个 AU 里有 **7 个没有任何权重**
（`eyeBlink*`、`mouthClose`、`mouthPucker`、`mouthRoll*`、`mouthShrug*`）⇒ 它们不参与打分，
也就不该参与"多区域佐证"。新用例把这条边界钉住（拉满这 7 个 AU ⇒ 区域命中必须为空）。

 * 全部在内存里改源码字符串，绝不写回仓库文件。 */
import { readFileSync } from "node:fs";
import { createContext, runInContext } from "node:vm";
import assert from "node:assert/strict";

const ROOT = process.cwd() + "/";   // 在仓根跑：node _test/js_engine_mut.mjs
const SRC = (rel) => readFileSync(ROOT + rel, "utf8");

function boot(globals, mut) {
  const ctx = createContext(Object.assign({ window: {} }, globals || {}, { console }));
  runInContext(SRC("src/data/emotion-lexicon.js"), ctx);
  runInContext(SRC("src/js/emotion-engine.js"), ctx);
  runInContext(SRC("src/data/face-smile-rules.js"), ctx);
  let eng = SRC("src/js/face-engine.js");
  if (mut) {

    assert.ok(eng.indexOf(from) >= 0, "变异锚点在源码里找不到（这条变异腿是假的）：" + from);
    eng = eng.replace(from, to);
  }
  runInContext(eng, ctx);
  return ctx;
}

const results = [];

  let red = false, note = "";

  results.push({ name, red, note });

// 变异 1：capability 的"非安全上下文"分支被摘掉 ⇒ ①那条腿必须红
leg("capability 摘掉 insecure 分支", () => {
  const c = boot({ window: { isSecureContext: false }, navigator: { mediaDevices: { getUserMedia() {} } } },
    ['if (!window.isSecureContext) return { ok: false, reason: "insecure-context" };',
     'if (false) return { ok: false, reason: "insecure-context" };']);
  assert.deepEqual(JSON.parse(JSON.stringify(c.window.FaceEngine.capability())),
    { ok: false, reason: "insecure-context" });

leg("setEnabled(true) 改写成写 on", () => {
  const m = new Map();
  const api = { getItem: (k) => (m.has(k) ? m.get(k) : null), setItem: (k, v) => m.set(k, String(v)),
                removeItem: (k) => m.delete(k) };
  const c = boot({ window: { isSecureContext: true }, localStorage: api },
    ["if (on) localStorage.removeItem(CAM_KEY);", 'if (on) localStorage.setItem(CAM_KEY, "on");']);
  c.window.FaceEngine.setEnabled(false);
  c.window.FaceEngine.setEnabled(true);
  assert.equal(m.has("peiliao.face.cam.v1"), false, "开启应当删键");
});
