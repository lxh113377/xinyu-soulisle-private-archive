> peers 侧取公开资料（README / 源码 / issue），逐条标出处，**不写成"全部现测"**。
> 社区协作（issue/PR）沿用 r100 §2.6 裁决：对标登记全是能力位对比，非对方缺陷 ⇒ **零动作**。

> 磁盘上判据早已声明 5 类，不是 3 类；但那 5 类里有 3 类**实际判不出来**，

> 这个区别决定了改造方向 —— 加类是治标，**标定 + 可证伪判据**才是治本。

## 1. 现状核验（先证现状，再谈对标）

### 1.1 老大前提的实测更正

磁盘实况（`src/data/face-smile-rules.js` r87 版）：判据声明 **5 类**
（joy / sadness / anger / fear / calm），不是 3 类。但把 5 个类的合成向量与
**教科书最大值**（AU 给到 0.8–1.0）跑一遍，分类是全对的：

```
真笑Duchenne → joy · 社交笑 → joy · 悲伤AU → sadness · 愤怒AU → anger · 恐惧AU → fear
```

可一旦按**真实摄像头的强度**（AU 0.15–0.5）重跑，结论就变了：

```
强度扫描（同一 AU 逐步减弱，看主情绪何时翻转）
scale=1.00  joy:joy  sadness:sadness  anger:anger  fear:fear   disgust:anger  surprise:fear
scale=0.50  joy:joy  sadness:sadness  anger:anger  fear:fear   disgust:calm   surprise:fear
scale=0.25  joy:calm sadness:calm     anger:calm  fear:calm   disgust:calm   surprise:calm
scale=0.15  joy:calm sadness:calm     anger:calm  fear:calm   disgust:calm   surprise:calm
```

⇒ **真实强度下，低强度的 sadness/anger/fear 全部退回 calm**；用户看到的就只剩
「平静 / 愉悦 / 强时的焦虑」，**与老大的体感完全吻合**。三类幻觉来源（surprise / disgust /
contempt）则根本不在词表里，只能挤进 anger / fear —— 所以「厌恶」被读成「烦躁」、
「惊讶」被读成「焦虑」，用户自然觉得"就那三种"。

### 1.2 三个硬缺陷（本轮全部实测复现）

| # | 缺陷 | 实测读数 | 用户体感 |
|---|---|---|---|
| **D1** | **判据从未被真实数据校准** | F5 只验 smile/neutral 两类的口部分离，权重表 4 组里有 3 组（sadness/anger/fear）**没有任何真实样本走过** | 「识别不准」 |
| **D2** | **三类情绪判不出来** | disgust 1.00 → **anger 0.47**；surprise 1.00 → **fear 1.00**；轻蔑 → joy | 「种类单一」 |
| **D3** | **强度饱和，高段无分辨力** | 强度分布 median=0.73、**25% 的帧顶满 1.0** | 「笑得很大和笑到极致一样」 |
| **D4** | **假阳性：专注＝愤怒** | 压眉 0.4（专注常态）→ **anger 0.39** 压过 calm；「说话+微皱眉」→ anger 0.33 | 「莫名其妙就烦躁了」 |
| **D5** | **无「看不出来」的出口** | 实测强度 p25 仅 0.47 ⇒ 一半帧本就不确定，却**每帧都硬给一个确定结论** | 「读数乱跳」 |

复算命令（全部零依赖、秒级）：
```
python _test/face_discrim_check.py            # 本轮新增的分类判别力尺
python _test/face_discrim_check.py --selftest # 证明这把尺有牙（5 条反例必须全被抓到）
```

### 1.3 一个必须记下来的方法论教训

本轮中途我做过一次**错误的"简化"**：因为用「用力压眉 0.95」测不出差别，就判定
多线索佐证规则（`need`）是死代码并删掉了它。删完 F11 立刻红 ——
「压眉 0.4」这档**轻皱**又变回 anger 假阳性。

> 假阳性恰恰发生在**低强度**那档（专注时人不会用力压眉）。
> **拿高强度向量去验低强度缺陷 = 验错了对象**，而高强度样本恰好是"看起来正常"的那个。
> 写在这里是因为：这是本轮唯一一个「我以为在简化、其实在删判据」的错误。

### 1.4 判据自身的两次返工（都是判据抓出来的，不是我看出来的）

| # | 现象 | 真相 | 处置 |
|---|---|---|---|
| **E1** | F11 报 8 条「强度非单调」 | **判据自己量错了对象**：它拿「当前主情绪」的强度去判「某个类的分数」单调性；而同一向量压弱后 argmax 会合法地退回 calm，此时报的是 calm 的分 | 改判据口径为「该类自己的分数」（探针回传全类分数快照 `pairs`） |
| **E2** | 强颜欢笑被判成 calm | **代码默认值与它自己注释里写的不一致**：注释说 `need` 默认 1（只对 anger/fear/sadness 生效），代码却写成默认 `R.cue.need`=2 ⇒ joy 也被要求两区，而「社交性微笑按定义就是只有口部参与」 | 代码改成默认 1，与注释对齐 |

> **E2 的教训比 E1 更值钱**：注释写了不等于代码是那样。
> 这条错**只有拿真实向量跑才看得见**，因为任何「看起来对」的向量（比如真笑）都恰好满足两区要求。
> 推论：**凡是「我以为它在起作用」的规则，都要专门造一条「它不起作用」的向量去证伪它。**
> —— 本轮 F11 的 selftest 就是把这件事机制化：把判据改坏，看尺抓不抓得到（6 条反例）。

### 2.3 逐项差距说明（量化）

#### ① 功能覆盖 — 心屿**落后但方向可辩护**

| 项 | 心屿 r101 | 对标 | 差距（量化） |
|---|---|---|---|
| 可判情绪类数 | 5（**实得 3**） | emonet **8** | **−3 类**，且实测 3 类不可靠 |
| 分类概率输出 | ❌ 只有 0–1 分，无分布 | face-api.js 给 **7 类 softmax 概率** | 缺"分布"信息，无法做「不像任何一类」的判断（D5 根因） |
| 连续情感维度（valence/arousal） | ❌ | emonet **CCC 0.82/0.75** | 缺一条**连续轴**，无法表达"难受但平静"这类混合态 |
| Duchenne 真/假笑 | ✅ **本仓独有** | emonet ❌ / face-api ❌ | **+1 项领先**（老师点名的问题） |
| 三路分歧标注（表情/文字/语音） | ✅ **本仓独有** | 同赛道均无 | **领先** |

> **关于「为什么不上 8 类」**（这里有个容易做错的决策，写清楚免得后人"顺手对齐"）：
> emotion-lexicon.js 是 **JS/Java 双端 SSOT**，给它加类要连带改 Java 侧 + 评测集 + 守卫。
> 而表情的类别上限由 **blendshape 决定，不由词表决定** ——
> disgust(AU9+AU10) 与 anger(AU4) 在口鼻区高度重叠，**不新增类就必然误判**（实测已证）。
> ⇒ 表情侧在 `face-smile-rules.js` **自持 8 类**，与文本侧的语义关系写在 `family` 字段，
> **不碰双端 SSOT**。这是权衡，不是遗漏。

#### ② 技术架构 — 心屿**有取舍，无落后**

心屿的「零构建纯静态」是**为这个项目定下的硬约束**（iCAN 评委要能直接打开就跑），
mediapipe 的 C++/多语言绑定、emonet 的 PyTorch 在这个场景**反而不可用**。
**差距不在架构，在"能力位"**：mediapipe 给 52 维原始 AU，心屿在其上再做一次语义映射 ——
多了一层推理，也就多了一份**需要被校准**的负担（正是 D1 的来源）。

#### ③ 实现方式 — 心屿有一处**明确落后**

- emonet 在 README 直接给出 **ACC / CCC / RMSE**，可复算；
- face-api.js **至今没有准确率数字**（issue #766 提问，官方未答）；
- 心屿 r101 **也没有任何"表情识别准确率"数字** —— F5 只验 smile/neutral 的可分性。
  ⇒ **本仓与 face-api.js 同病**，而与 emonet 的差距是**可补的**（见 §3 改进项 ①④）。

#### ④ 性能 — 心屿**优势项**

13.7MB 模型走**懒加载**（用户点开才下）、8fps 采样、EMA 平滑、单文件判据无运行时开销。
mediapipe 原生同样端侧；emonet **完全不适用**（离线 GPU）；face-api.js 310KB 更小但能力位低。

#### ⑤ 可扩展性 — 心屿**本轮的最大反转**

- face-api.js **作者明示不可扩**（issue #232："It's not possible to extend the current
  model like that… you will have to train your own model"）⇒ 类别写死在网络输出层。
- 心屿因为走**可解释规则**而非分类头，**加类是改一张权重表** —— 本轮 5 类→8 类即实证。
  ⇒ 心屿在这一维**结构性领先**，且这是"零训练"换来的代价可控。

#### ⑥ 维护状态 — 心屿**落后**

| | 最近更新 | issue 响应 |
|---|---|---|
| mediapipe | 活跃（Google 官方） | 正常 |
| face-api.js | ⚠️ stale | issue #766（2021 问准确率）**至今无官方回答** |
| emonet | 论文配套，冻结 | — |
| **心屿** | 单人项目 | 无 issue 面，靠仓内判据自守 |

> face-api.js 的 stale 印证了一条判断：**选一个停更的库当依赖，不如选一个能自解释的规则。**
> 这也是本仓判据 SSOT 路线的间接支持。

#### ⑦ 文档完善 — 心屿 r101 **落后，本轮已补**

r101 的 `face-smile-rules.js` 记了 Duchenne 阈值的标定，**但没记其余权重的标定依据**。
本轮补：每个易混对的**分水岭是什么**（上唇上提 / 下颌方向 / 眼周参与 / 左右不对称），
以及标定依据搬进 memory（省预算，见 §3 改动②）。

#### ⑧ 适用场景 — 心屿**最匹配**

浏览器 · 零构建 · 无需训练数据 · 无 GPU · 评委双击即用。
emonet 需要 AffectNet（40 万张标注）+ GPU；face-api.js 需要 TF.js 运行时。

### 4.1 四项改造的优先级排序依据（老大明确要求）

| 顺位 | 项 | 为什么排这里 |
|---|---|---|
| 1 | **F11 判别力尺** | 它是**其余三项的验收面**。没有它，后面每一项都是"我觉得改好了" |
| 2 | **重标 peak** | 消除饱和是**误报的总开关** —— 弱信号被顶到 1.0 是 D4 的直接成因；且不动它，D2 的新类同样会被压到饱和 |
| 3 | **5 类 → 8 类** | 收益直观，但**必须排在标定之后**：没标定就加类，只是把 3 个错类变成 6 个 |
| 4 | **family + 置信度 + 接线** | 属**表达层**（把已有能力如实呈现出来），不改判别力，故最后 |

### 4.2 预期目标 vs 完成标准（逐项）

| 项 | 预期目标 | 完成标准（实测回执） |
|---|---|---|
| F11 | 「情绪种类单一」有人拦 | `F11-PASS 分类 17/17 类别 8 饱和 2/60 低置信 1`；`F11-SELFTEST-PASS 实跑 6 条反例，全部被 F11 抓到（判据有牙）` |
| peak | 高强度段恢复分辨力 | 饱和 25% → **3%**；三档递增断言通过（0.367 < 0.504 < 0.917） |
| 8 类 | 三类不再被抢占 | disgust − anger > 0；fear − surprise **0.135**（门槛 0.10）；对称笑时 contempt **严格 = 0** |
| 置信度 | 「看不出来」有出口 | 弱恐惧 margin 0.090 → `confident=false`；对照厌恶 margin 0.457 → `true` |
| 单测 | 判据自身有牙 | `node --test`：18 tests / **18 pass** / 0 fail（r87 是 10 例） |
