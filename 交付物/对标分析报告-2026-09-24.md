## 2. 逐项差距说明（本项目对应部分 → 差距）

### 2.1 功能模块覆盖
- **对应部分**：`src/js/emotion-engine.js`（双路情绪）、`chat-agent.js`（对话）、危机转介、`memory-store.js`（J4 记忆）。
- **差距**：① 无 SSE/流式输出——对标项目聊天类标配（LobeChat fetch-sse、OLV WebSocket），心屿 `/api/chat` 整包返回，首字延迟≈完整响应时间（实测在线 965ms 为整包）；② 单一模型供应商（DeepSeek），无 `LLM_PROVIDER` 适配层；③ 无 TTS（回复不能"说"出来，陪伴感短板）；④ 无多角色/人设系统（SillyTavern 角色卡、LobeChat 助手市场均为此类）。
- **心屿反超点（应保持并宣传）**：危机拦截三项目全 ❌；评测集可现场复跑（98.6%/73 条）三项目全 ❌——这是"情绪识别"从口号变成可验证指标的唯一实证。

### 2.2 技术架构与实现方式
- **对应部分**：零构建静态前端 + Serverless v1 + Spring Boot v2 三层并存。
- **差距**：无状态管理框架与组件化（原生 ES Module 手写，Lobe 用 Zustand+React）；后端单体无任务队列。
- **判定**：**这不是缺陷而是选型**（决策 #1/#2 已记录：零构建换来"评委免环境直开"，直读 `src/` 换来零副本）。架构维度无需向 React 系看齐；真正该抄的是 LobeChat 的**模型适配层抽象**（接口形状：provider 注册表 + 统一 `/chat/completions` 出口，心屿函数侧已是 OpenAI 兼容，改造成本低）。

### 2.3 性能表现
- **对应部分**：Three.js 逐粒子星雾 + GSAP 滚动。
- **差距**：① 无流式（见 2.1）；② 长对话列表无虚拟化（Lobe 用 react-virtuoso），心屿对话坞累计数百条后 DOM 增长未治理；③ 无 PWA/离线缓存（vendor 本地化已部分弥补——断网可开但缓存语义不受控）；④ 移动端仅 1 条 640px 媒体查询。
- **实测无差距项**：首屏零构建直开、WebGL 降级 CSS、LLM 不可达 3ms 回落离线——降级链路速度优于对标项目常见水平（❌未做同口径对比实测）。

### 2.4 可扩展性
- **差距最大维**：无插件/扩展机制、无配置化的情绪策略路由（共情策略硬编码于 `chat-agent.js` 模板与 prompt）。LobeChat 有 SDK+网关+仓库索引三件套；SillyTavern 有扩展市场。
- **务实评估**：参赛作品不需要插件市场，但需要**"加一个新情绪类别只改一处"级别的配置化**。词表 SSOT 化（e79025b）已完成第一步；策略路由表化是第二步。

### 2.5 维护状态
- 心屿每日提交、判据全绿，活跃度过硬。差距在**对外可见性**：无 release tag、无语义化版本、无 CHANGELOG（三者全有于对标项目）→ 本轮补 CHANGELOG + 建议打 tag。
- 参照教训：Open-LLM-VTuber 13.9k★ 也近 4 月停更——热度≠可持续，比赛交付后心屿的维护节奏应有明示的 roadmap 而非静默。

### 2.6 文档完善程度
- README 已达"结构完整"（badge 级要素中缺：badge 群、可折叠 TOC、Star History、英文版、环境变量专节、贡献/安全链接）。对标三家全部具备其中 ≥4 项。→ **本轮已全部补齐**。
- `memory/` 交接体系（01–08 + 分卷 + 绑定表）是**超出全部对标项目**的工程实践，但对外不可见（参赛材料可在附录节选展示）。

### 2.7 适用场景
- 心屿（高校情绪倾诉/独居青年）与三家（通用聊天/桌宠/角色扮演）**场景不重叠**，且三家均无医疗免责+危机转介设计。差异化定位成立，报告中建议答辩时直接引用"三对标项目危机干预均缺失"作为创新点实证（创新 30 分维度）。
