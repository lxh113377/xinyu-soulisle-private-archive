## 2. 逐项差距说明

### ① 性能维：本轮翻掉的两格（0/16 → self 1/16）

r89 时 `ci_perf_step` 与 `published_numbers` 是 self 同址尺上**仅有的两格假**，而这两格在 16 个参照仓里是 **0/16**——即"全行业共同缺失"。共同缺失不等于不该做：性能是八维里唯一"有没有数"可以直接影响评委判断的一维。本轮做了三件事（§4 #1–#3），翻真后：

- `ci_perf_step`：证据 `.github/workflows/perf-baseline.yml`（真跑 `perf_baseline_check.py`，非占位文件）
- `published_numbers`：证据 README 实测行 `P95=28.6ms … 吞吐 1013.9 rps`

**为什么不是"为了翻格子而翻格子"**：性能判据本体 r40 就在，一直只在本地电池里跑。接进 CI 的真实收益是"退化在受理面上会红"，格子翻真只是副产品。反过来若只改文件名、不真跑判据，就是 r41 那一族"门禁在受理面上静默消失"——所以本轮同时上了 `ci_perf_wiring_check.py` 盯住五条接线（§4 #3）。

### ② 能力维：双标消除后的**反向结论**（本轮最重要的一条）

r89 §2③ 把 `streaming`/`e2e_browser` 记为"测量盲区，要翻这格必须 16 仓同址换尺"。本轮把第二通道（内容法）同址跑到了 self 上，结果分两半：

| 格子 | 同址前（r89 说法） | 同址后实测 | 结论 |
|---|---|---|---|
| `streaming` | self 是盲区（只靠 `caps_blind` 自述） | `token_stream`（README 里"逐字流式输出 / SSE 直通"被同源正则认下） | **自述属实**，且现在有尺 |
| `e2e_browser` | self 是盲区 | **第一次跑 = `none`** | ⚠️ README 里根本没提浏览器回归 ⇒ 内容法看不见 |

第二格暴露的是**真问题不是尺的问题**：`_test/browser_check.py` / `pixel_dual_check.py` 确实用 Playwright 真开 Chromium，CI 也真装了 chromium，但 README 一行没写。也就是说——**r89 那句"内容里有证据、只是尺看不见"，有一半其实是"我们没在任何对外面上写过"**，和对标里判 peers 的"机制有、文档无 = 不可发现"是同一条缺陷，这次砸在自己身上（这是本项目该口径陷阱的第 5 例：r52 记忆落库 / r50 dependabot alerts / r70 vector_memory 假阳 / r89 人读手册无读者）。

处置：README 补一段**如实描述**的浏览器回归说明（不是为赢格子编的，它本来就是真的），复采后 `e2e_browser=test_e2e`。

**并且要写清天花板**：内容法量的是**公开主张**，不是代码事实。self 的输入面比 peers **更窄**（peers = description + homepage + README，self 只有 README blob），所以"命中即为真，未命中只说明没写"——这条对两侧同效，任何一侧都不许拿 `none` 下"没有该能力"的结论。
