## 2. 逐项差距与一手发现（全部可复算）

### 2.1 🔴 版本三源断链：`v1.8.2` tag 根本不在 main 的祖先面上（维度 6）

`repo_config G12` 报「tag=v1.8.2 而 pom=1.8.1」已挂了两轮，前两轮都写成「切版动作待老大裁决」。
本轮把 tag 本身查了一遍，**这句归因不完整**：

```
git log -1 v1.8.2                     = e8462ca chore(release): v1.8.2 —— 三源同步（pom/ROADMAP/CHANGELOG）+ annotated tag
git show e8462ca:server/pom.xml       = <version>1.8.2</version>
git merge-base --is-ancestor e8462ca HEAD = 非零 ⇒ e8462ca 不在 main 历史上
git ls-remote --tags origin           = refs/tags/v1.8.2 → 158fc59（peel 到 e8462ca）—— 远端已有这枚 tag
HEAD 的 server/pom.xml                = <version>1.8.1</version>
```

**结论**：v1.8.2 那次发版是在**旁支提交**上完成的（r101 记录过绕行手段 = 临时 clone + cherry-pick），
tag 已推到 origin，但那笔「三源同步」的正文从未进 main。所以今天两侧都是真的、且互相矛盾：
远端存在一个指向 main 之外内容的 release tag，而 main 的 pom 仍是 1.8.1。

### 2.1b 🔴 比 G12 更重的一层：`origin/main` 与本地 main **已经分叉**（本轮收尾实测）

G12 只说"三源不一致"。把远端指针量出来之后，问题的形状变了：

```
git ls-remote origin refs/heads/main            = e8462ca（远端 main 正停在"那笔旁支发版提交"上）
git rev-list --left-right --count origin/main...HEAD = 18  41   （远端 18 条本地没有，本地 41 条远端没有）
git show --stat e8462ca                          = CHANGELOG +4 / ROADMAP 1-1+1 / server/pom.xml 1-1+1（只改版本号三处）
git log --oneline HEAD..origin/main              = r100/r101 那 18 条原文
git log --oneline --grep=r101 HEAD               = 本地有 8886ef7 / 298f76a / 1662946…（同内容不同 SHA ⇒ cherry-pick 版）
```

⇒ **真实形状**：本地 main 是"r101 工作的 cherry-pick 重放 + r102…r105"，远端 main 停在"r101 原文 + 一笔只改版本号的 v1.8.2"。
本地缺的**内容**其实只有那笔版本号增量（3 个文件、6 行）；本地多的 41 条里含 r102–r105 全部成果。

**为什么本轮不推**：这种分叉下普通 `git push` 必被拒（non-fast-forward）；要推只能
**merge 把远端旧线并进来**（多一次冲突处理，且把重复内容并两遍）或 **force-push**
（**重写已发布历史**，让远端那 18 条 SHA 引用与 `v1.8.2` tag 一起失效）。
按 #25② 与在册的「force push 与历史重写仍需确认」，这属**重大且不可逆**，
**已停下等老大选**（不是"忘了推"）；`post-commit` 也帮不上——本仓钩子里零 `git push`（`grep -c "git push" .git/hooks/post-commit` = 0），
自动推送那条经验只覆盖 iCAN / global_skills / global_memory 三仓。

两种收口方向的**代价**（本轮未做，等选定后做）：merge 一侧先在副本仓实测冲突数与重复内容形态，
再谈要不要在正式仓动；force 一侧必须先取远端 SHA 的备份（`git bundle`）并确认无他人正基于 e8462ca 工作。

这**不是**「还没切版」，是「切了但没落地」，而且落地那条线**成了远端 main 本身**。两种收口方向都改对外可见面，故本轮只报告不动手（§3 登记不执行 ⑤）。

### 2.3 🔴 唯一实现棘轮被新增手写回退顶高（维度 3，E2）

r96 立 `browser_engine` 时量出 29 份手写回退，r98 起改为**只许降不许升**的上界。本轮现读 **24 > 基线 23**：
新增套件（含 `dock_auto_check.py`）又抄了一遍 `try: chromium.launch() / except: launch(channel="msedge")`。

### 2.4 🟠 仪器崩溃族：6 条 BLIND-RED，本轮关掉 2 条（维度 3/4）

`vendor_freshness_check.py:58` 假设名册每条都有字符串 `detect`；并行会话在途的
`_test/vendor-manifest.json` 新增 4 条 mediapipe 条目写的是 **`"detect": null`**（模型/wasm 无版本横幅可解析）
⇒ `re.search(None, …)` 抛 `TypeError`，判据连结论行都没印出来就死了，`--selftest` 同死。
这就是电池把 6 条判据归入 **BLIND-RED(判红却无任何判据结论行 ⇒ 仪器崩了，不是产品红)** 的原因：
**崩溃的一方看不出自己瞎了**，其余 V1/V3 有没有跑过无人知道。

另 4 条 BLIND-RED（`j4_memory / browser_check / pixel_dual / lightshow`）本轮定位到形状但**不属本轮责任面**：
- `lightshow_check` 死于自己的**对照组**：`AssertionError: 判据失效：未点亮时也判出这些颜色: ['低落','平静']`
  —— 星雾基色变了（并行会话在途 `three-scene.js` +31/-2、`style.css` +49/-22）。这是**真信号**，不是噪声：
  要么基色真的污染了"未点亮"态，要么对照组的颜色取样口径需要跟着新调色板走。**归其作者判**。
- `j4_memory_check` 死于未捕获的 `playwright TimeoutError: Page.wait_for_function 15000ms` ⇒ 同一族的
  **第二种崩溃形态**（等待超时应当判「未验/点名红」，不该抛栈）。登记给下一轮，见 §3 ⑥。

### 2.6 🟠 共享端口 8123 无属主协议（维度 3 的复现性地基）

**下一次 rebuild 就会再杀一次**。

## 7. 本轮最值得留下的三个可复用件

1. **`build_jar.classify_holder()` + `stop_plan()`** —— 「杀进程之前先问是不是我起的」的最小完整形态：
   四档归类（含 `unknown`= 取不到命令行 ⇒ **绝不升格成可杀**）、默认只停 ours、`--takeover` 是人明确授权的口子。
   任何按端口/按名字清理进程的工具都能照这个形状改。
2. **`vendor_freshness.field_problems()`** —— 台账解析器的「五字段缺失/类型门」范式：
   不可解析 ⇒ 点名条目与字段并继续跑其余判据；`null` 是**一档合法声明**（只关掉它自己那条腿），
   缺键与错类型才是红。**崩溃与判红与环境三分**才谈得上归因。
3. **「接线两侧先测」这条纪律** —— 把孤儿判据接进阻断链之前，HEAD 面（=CI 会跑的那份）与工作树面
   各自实测 PASS。否则"接线"这个动作本身就可能是一次引入新红。
