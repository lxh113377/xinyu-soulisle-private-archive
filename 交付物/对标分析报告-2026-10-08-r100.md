## 2. 逐项差距说明（本轮一手发现，全部可复算）

### 2.1 判据的失败路径自己会崩，而且崩得没有声音（高，维度 3）
三处的实测形态：`clean_clone_check.py:163` 的 `pg.goto(wait_until="networkidle")` 裸奔；
`rescan_shots_check.py:68` 的断网 `pg.reload(timeout=25000)` 裸奔；`public_check.py` 全文用裸 `assert`
（失败 ⇒ `AssertionError` traceback，**不含 PASS/FAIL 判据词** ⇒ 电池"只留最后一行判据词"的折叠规则下
这条套件在 CI 里等于没有结论）。后果是 **rc=1 的判红名单里混进了仪器崩溃**，归因要花一整轮。
复算：`python _test/clean_clone_check.py --nav-timeout 1` ⇒ rc=1 且门面行点名
`TimeoutError: Page.goto: Timeout 1ms exceeded`，C3/C4/C5 各记未验（分母不缩水）。

### 2.2 每档跑 5 次取中位数，**没有**把跨轮噪声压下来（高，维度 4）
入口第②条写的是"把检测限从 50% 往下压"。实测否证了它——这是本轮最重要的结论，写在权威面
`docs/PERF-BASELINE.md §1b`，台账 10 份同口径件可复算：

| 档/面 | 跨轮带宽（10 轮 max/min） | 相邻轮最坏差 | 在 ±50% 下可判？ |
|---|---|---|---|
| t8/health | 65.9% | 55.9% | ❌ |
| t8/emotion | 55.9% | 49.9% | ❌（零余量） |
| t16/health | 71.3% | 71.3% | ❌ |
| t16/emotion | 76.7% | 76.7% | ❌ |
| t32/health | 16.6% | 14.2% | ✅ 余量 ~3× |
| t32/emotion | 12.8% | 12.7% | ✅ |
| t64/health | 12.2% | 7.9% | ✅ |
| t64/emotion | 9.2% | 8.8% | ✅ |

机理：同一轮里的 5 次 reps **共享同一台机器的同一时刻**，噪声是相关的，重复不产生独立性；
压得掉的是采样次数那一半（档内带宽中位 14.0%~15.2%），压不掉的是轮与轮之间的机器状态。
⇒ **阈值一字未动（仍 ±50%）**，没有把检测限往下压的资格就把阈值调小，等于逼下一轮虚报。
到手的东西改成两件可复算的：① 台账自报噪声底（`band_rps`/`reps`/`reps_warmup_dropped`/`worst_band_pct`）；
② 漂移尺 `noise_floor()` 把「本轮该档带宽 ≥ 阈值」的档面点名成**噪声档**（红照判、rc 不放宽）。

### 2.3 命名纪律会让"相邻两份"变成"首尾两份"（中，维度 4/7）
`ledgers()` 按 `(文件名日期, 文件名字典序)` 取相邻两份，而 `.`(0x2E) > `-`(0x2D) ⇒ 当天**第一份**若写成
无后缀（`…-10-08.json`）会排在 `…-10-08-b.json` **之后**。本轮真踩：漂移尺比的成了「第一份 vs 最后一份」，
当场产出 2 条 `t16 p95 +67.9%` 的**假红**（什么都没坏）。已把该份改名 `-a`（现 a..j 严格时间序），
纪律写进 `docs/PERF-BASELINE.md §1b` 与 `docs/quality-gates.md`。复算：`python _test/perf_ramp_delta_check.py`
⇒ `PERF-RAMP-DELTA-PASS … 红0`（相邻两份）。

### 2.4 一条产品钩子的代价：公网面差距从 1 件变 2 件（中，维度 8/交付）
③ 落地后 `live_sync` 现点名 `js/chat-agent.js(live=14699B local=15225B)` ＋ 原有的 `js/voice.js(4148/4798B)`。
这**不是新缺陷**，是同一件老事的又一次显形：公网主推面仍跑 r97 之前的语音模块 + 本轮之前的 chat-agent，
解封前提仍是 Cloudflare API Token（P0 在册）。对外表述必须带"哪一层"（本地 jar / deploy 副本 / 公网）。

### 2.5 peers 侧重采的覆盖度与没采到的代价（方法论，维度 1/3/7）
本轮按入口第①条做**错峰单跑**：16 族逐个跑、族间 sleep 20s（禁 burst，承 r96 撞限流的一手代价）。
结果 **16/16 落盘、龄全为 0 天**（`python _test/ledger_age_check.py` ⇒ `LEDGER-AGE-PASS 线内 16｜超 fuse 0`）。
但 **5 族 rc=1**，逐条归因，既不折成"重采失败"也不折成"全绿"：

| 族 | rc=1 的原因 | 判据自己的处置 |
|---|---|---|
| `peer-community` | 16 仓里 **5 仓 `http=403`**（GitHub secondary rate limit） | `usable 11 + blind 5 == 16` 恒等式成立；NA **绝不并入"零 PR"**（该族在册就被这条塌缩骗出过假结论） |
| `peer-hygiene` | 17 仓 × 字段级 **6 个 NA**（`HYGIENE-PROBE-PARTIAL`，整仓取数失败 0） | 字段级 NA 出声，不冒充完整 |
| `peer-issue-response` | 9 格 NA——多数是**本来就没有已关 issue**（人口=0 / 窗口内 0 / 样本 n<3） | 恒等式 `8+8==16` 成立；"没人提过"≠"响应慢" |
| `peer-maintenance` | 2 仓两腿不等（分页法 2 / search 法 1）⇒ **该格判不可用，不取平均** | self 历史跨度 16 天 < 30 ⇒ 明写"无横比资格" |
| `peer-mobile` | 2 仓无 CSS 件记 NA + 4 仓范围外（非 Web 面） | 恒等式 OK，可用 10/16 |

**本轮新发现的一条口径缺口（登记 §4 r101）**：`ledger_age` 的 degraded 面按**文件位置**判（在 `_partial/` 里才算
degraded），所以这批 PARTIAL 件在它眼里是"新鲜"——**按日期新鲜 ≠ 按取数完整**。上一轮那份
`peer-hygiene-2026-10-05.json` 至今仍在 `_partial/` 里被单独计数，而本轮这份 PARTIAL 的 `-10-08` 不会。
⇒ 维度的 peers 列本轮是**现测**，但凡来自上述 NA 格的读数一律标"未取到"，不写"全部现测"。

### 2.6 为什么不向 peers 提 issue / PR（沿用老大裁决，此处记依据）
对标 16 仓的缺陷登记全部是**能力位对比**，不是"发现对方有 bug"；本轮唯一带对方缺陷线索的仍是
`MoodChat` 两腿不等（维度 6），那是对方取数问题不是代码缺陷 ⇒ 社区协作零动作。
