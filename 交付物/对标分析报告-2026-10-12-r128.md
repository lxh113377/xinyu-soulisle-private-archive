## 2. 逐项差距说明

### 第 5 维（可扩展性）—— 唯一「self 零位而对手有分母」的维度，本轮缩小了一格

- **对手有、我方零**：向量/语义长记忆（`airi/packages/memory-pgvector` 目录实测在册；r127 口径 pool 内 9/16）。
- **我方现状**：改造前只能 `?limit=` 倒序翻页，等于**只能按时间找、不能按内容找**。
- **本轮动作**：补 BM25 检索（`GET /api/memory/search`），把「按内容找」这条能力从 0 做到 1。
- **为什么不一步到位做向量**：架构决策 #1 写死了「需要 Embedding/向量检索时，形态应是 Java 管业务 API + Python 管模型服务」。上向量 = 当场推翻该决策 = 要老大拍板的事。**一个自动化轮不该单方面干。**
- **量化差距**：语义泛化能力仍缺（BM25 只能字面/二元组桥接，「心烦」检索不到「烦躁」）；渠道适配 0（lobe-chat 有 4 条）；插件协议 0（pool 内无分母，不构成可比差距）。

### 第 1 维（功能覆盖）—— 本轮补的是「防滥用与可观测」，不是「加功能」

- **`/api/chat` 是本仓唯一花钱的端点，而它零防护**：实测全量 grep `rateLimit|RateLimit|429|quota|Retry-After` 在 `server/src/main/java` 下 **0 命中**。任何人拿到演示地址即可无限次烧上游密钥。
- **对手有**：lobe-chat 实测存在 `packages/heterogeneous-agents/quota`（`quotaCalendarModel.ts` 全文已读：usage ledger 出每日 token/花费、会话窗口与 7 日周窗口两级限额、burn-down 曲线与耗尽预测）。
- **我方现状（改造前）**：无限流、无用量台账、无访问日志（全仓仅 `ModelProxy` 一处 slf4j）。
- **量化差距**：成本控制位 **0 → 3**（限流 / 体上限 / 结构化日志），可观测位 **1 个类 → 1 道横切过滤器**。

### 第 3 维（实现方式）—— self 仍是池内最强，但**测试规模本身是新风险**

- 优势可复算：判据 133 件 / 38,339 行 vs 产品代码 `src/js` 3,608 + `server/main` 1,595 = **5,203 行**，比例 **7.4:1**。
- ⚠️ **反向发现**：这个比例本身是待办不是成绩。判据层已占仓库体量的绝大部分，维护成本与「判据本身出 bug」的耦合面都在上升（r127 §8 一轮之内就出了 S8/S9/S10/S11 四处**判据自身缺陷**）。本轮我又亲手犯了两处同类（§7 归因表第 5、6 行）。

### 第 4 维（性能）—— 明确写「不可测」，不拿体感冒充数字

- pool 内 16 仓 `bench measured*=0/16`（r127 现读）⇒ **没有任何一条可复算的横比基准**。
- 本仓有 `perf-baseline.yml` 与 `size_budget_check.py`，但那量的是**首屏体积**，不是响应时间/并发。
- **结论**：性能维本轮**不出数字**。给一个「我们更快」的说法在当前证据下是不可复算的空话。

### 第 6 维（维护状态）—— 发版链断链，本轮不修

- 实测：`git tag` 最新 v1.8.2，`server/pom.xml` 为 1.8.1 ⇒ G12 判红。
- **不修的理由**：切版会覆盖他人 8123 在服务产物 + 需要授权（r127 §3 已列为「本轮不做」并顺延）。本轮不重复申请，只在 §3 里保留。

## 8. 一手教训（本轮新踩，与 r127 §8 同族）

1. **「对手有 X」必须落到文件路径才算取证**：`lobe-chat 有配额体系` 这句话本身不算证据，`src/features/AgentQuotaCalendar/quotaCalendarModel.ts` 全文读到 `from '@lobechat/heterogeneous-agents/quota'` 才算。
