## 2. 本轮核心发现：受理面三条真红（逐条 现象 → 归因 → 反例 → 修法 → 证据）

### 2.0 为什么前四轮没看见（这是本轮最该留下的一条）

| 时刻 | 判据说了什么 | 我们信了什么 | 实情（本轮实测） |
|---|---|---|---|
| r29–r30 | `CI-STATUS-RED`（账单/配额措辞） | "只有老大能解，我不动" | 真（当时 runner 从未启动） |
| r31–r34 | 同一行 `RED: ci_status` | 沿用上一轮归因 | **计费已恢复**，红的原因换成了代码级失败 |
| r35 本轮 | `HEAD 最近 run 判定 = CODE_FAIL` + 有真日志 | —— | 最近 5 次 main push **全部 failure**，两条 job 各有真实失败步 |

> 机制级教训：**"诚实保留一条红"这个决定，在红的含义发生变化后就失效了。**
> 电池收口行原先只印 `RED: <套件名>`，rc=1（判红）与 rc=2（环境未验）长得一模一样，
> 于是"换原因的常红"读起来与上周无异。这不是归因错误，是**判据没把变化的维度显影出来**。
> 已机器化：`run_all_suites.py` 收口行现分三类打印 —— `ALL-GREEN` / `RED(判红，必须修)` /
> `ENV-UNVERIFIED(不是判红，但不得声称已验)`（✅ 本轮实跑打印 `RED(判红，必须修): ci_status`）。

### 2.1 缺陷一：CI 密钥门禁被自家判据的测试样本命中（已修，判据同源化）

- **现象** ✅：同步守卫 job 的 `密钥零入库扫描` 步失败，输出只有一行文件名 `_test/pdf_leak_scan.py`。
- **归因** ✅：该文件第 91 行为"PDF 文本层泄漏判据"准备反例样本，写成连续的 `sk-` + 24 位字面量；
  CI 的门禁扫 `git ls-files`，用的正是同一条正则 —— **扫描器自己的反例把扫描器判红了**（R236 第二类"扫描范围含规则本体"的变体：命中的不是文档，是判据夹具）。
- **为什么本机看不见**：本地电池只有 `public_check`（扫交付副本），CI 那条是 yml 内联 bash —— **同一判断两处实现，只有一处会红**（M5⑥）。
- **修法**（三层，不只改样本）：
  1. 样本串改拼接 `"sk-" + "abcdefghij" + "1234567890" + "QRST"`，反例语义不变；
  2. 新建 `_test/tracked_secret_scan.py`：把判定收进**一处**（含 T1 分母非空断言 / T2 逐条 `路径:行号` / `--selftest` 四类边界）；
  3. `ci.yml` 的密钥步**改为调该脚本**（不再内联正则），并把它进电池 ⇒ CI 与本地从此同尺。
- **判据双向验** ✅：改动后 `SECRET-SCAN-PASS（跟踪文件 215 个，0 命中）`；
  变异体=把 `git show HEAD:_test/pdf_leak_scan.py`（改前原文）喂进 `scan_text` → 命中 `[91]`；
  临时造含密钥的跟踪态文件 → 命中 `[1]`；正则文本自身/短串/空输入 → 零命中（既防漏报也防误报）。

### 2.2 缺陷二：`voice` 判据的"CI 无麦克风"降级没盖住 A4（已修 + 顺手收紧）

- **现象** ✅：CI 上 `voice rc=1`，失败项 `A4 未观察到监听态`，而同一份输出里 `A7 SKIP 本环境无麦克风输入（CI）` 已经打印。
- **归因**：A7 有降级、A4 没有 —— 降级逻辑只覆盖了它自己那条断言。CI 事件序列实测 `['start','error:audio-capture','end']` ⇒ 无采集设备时 `recording` 类**不可能出现**，A4 断的是环境给不出的状态。
- **修法 + 收紧**：抽出纯函数 `no_input_device(ev)`（CI **且** 错误全部是 `audio-capture` 才降级），A4/A7 共用；
  同时把旧写法里并列的 `not-allowed` / `service-not-allowed` **踢出降级名单** —— 那是麦克风权限被拒，正是演示当天会真发生的阻断，跟着一起 SKIP 等于把缺陷藏进"CI 允许"。
- **反例（新增常驻套件 `voice_selftest`）** ✅ 5 例全过，含两个反向方向：本机同错误必须判红、CI+权限被拒必须判红、混合错误不降级、无错误不得拿环境当理由。

### 2.3 缺陷三：`settings_panel` 四条在 CI 红、本机 9/9 绿 —— **未归因，因此不声称已修**

- **现象** ✅：CI 上 S3/S4/S5/S7b FAIL，四条详情都是"配置一字未改"；同 job 里**唯一带等待的 S6 是绿的**。
- **已排除的变量** ✅：把公网零密钥 stub 复制成 `src/js/demo-config.js`（CI 的做法）复跑 ⇒ 本机 9/9 仍绿；前后按 sha256 还原（`2521954c…be6d0`），公网 stub 未触碰。
- **候选（未定案）**：`<dialog>` 表单-对话框语义未走到（`returnValue !== "save"` ⇒ 落盘处理器整体早退，且**不抛异常**，所以 S8 全程零 JS 异常也成立）；或点击未关窗。两者红法不同但现象相同，本机无法区分。
- **本轮处置 = 让判据自己说清**（不猜、不放宽）：
  1. `click_save()` 加完成态等待（测试侧**后注册** `close` 监听计数 ⇒ 排在应用写入之后），点了却没落盘会在 5s 后**超时判红**而不是读到旧值；
  2. `check(..., pg=pg)`：报红时自动附现场 `{open, returnValue, saveDone, domBase, cfg, ua}`，PASS 不刷屏；
  3. `--selftest` 增两类：⑥ **去测**"同步读 vs 等待后读"有没有差异 —— 本机实测**无差异**
     （`close()` 返回后同一次求值里已读到新值）⇒ 竞态假设**被当场否证**，不再当作 CI 那条红的解释；
     ⑦ 把保存按钮改成不关窗 ⇒ 完成态等待必须超时判红（已实测抓到）。
     ⑥ 的价值不在"证明了竞态"，而在**让本文件对"等待是否必要"持续持有证据**。
- **推送后的新事实**（run `36219657886`，见 §9.3）：加完成态等待之后，CI 上那四条**消失**（settings 全绿）。
  最终口径因此是：**修法有效已被受理面证实，机制解释仍不完整** ——
  本机测不到"点完就读"的差异，而 CI 侧一旦改成等完成态就绿 ⇒ 差异出在 CI 的时间/调度面
  （同一次求值边界在两平台松紧不同），不是产品的写入顺序。
  ⑥ 保留的意义正在于此：它让"等待是否必要"这件事**持续持有证据**，而不是靠一次性猜测定案。

## 10. r36 增补 · 行尾确定性（2026-09-26 上午，接 §6 优先级清单执行）

**为什么这一轮做这个**：§3 的"文档/工程配套"维度里我没有把 `.gitattributes` 当成一项差距——
直到本轮要让 `size_budget`（字节预算 831,152B）与 `deploy_sync`（SHA256 双向比对）两类主张
在**别人的 clone** 上成立。它们当前只在本机成立。

### 10.1 现象 → 归因 → 反例 → 修法 → 证据

| 环节 | 内容 |
|---|---|
| 现象 | 本机 `工作树字节 == 我算出的 SHA256`，但仓库 blob 是 LF、工作树是 CRLF；换一台 `core.autocrlf=input` 的机器 checkout，**同一份提交**文本字节就不同 |
| 归因 | `.gitattributes` 只声明了部分类型，`* text=auto` + 本机 `core.autocrlf=true` ⇒ 检出时 LF→CRLF，判据在工作树上量。"字节预算/SHA 对账"这类主张隐含前提是**行尾唯一**，此前无人钉住 |
| 反例（先证判据再动数据） | 归一后另建两份 clone，分别 `autocrlf=true` / `autocrlf=input` 检出 ⇒ 文本侧字节一致；再取一份**归一前**的旧检出对照 ⇒ 同一文件两种字节，差异 100% 落在 `0D0A` |
| 修法 | `.gitattributes` 钉 `* text=auto eol=lf` + `*.sh`/`*.ps1` 强制 LF + 20 类扩展名显式 `binary`；108 个文本文件 `git add --renormalize`；新增常驻判据 `eol_parity`（两条套件）+ 8 类自证 |
| 证据 | `EOL-PARITY-PASS（text=205 binary=20 total=225；工作树字节 == blob 字节 ⇒ 与机器无关）`；归一零内容改动由 `git diff --name-only` == `--ignore-cr-at-eol --name-only`（只差本轮 2 个有意改的文件）证明 |

### 10.2 本轮最贵的自伤：归一工具把二进制文件改坏了

首轮 renormalize 之后，20 个二进制里有 **`0D0A` 字节的被剥掉 1–2 字节**（PNG / MP4 命中）。
守卫当时没拦住，原因是它做的是"两侧都归一后再比"——**两侧被同样破坏，差值仍是零**。
处置：全部 `git show HEAD:<rel>` 还原，复核余 0 条不等；并把该形状固化为判据规则 **E3**
（文件含 `0D0A` 却未声明 `binary` ⇒ 判红）。
同时**撤销我自己一开始写严的另一半**（"声明了 binary 就必须含 `0D0A`"）——那是把
"本轮见过的 binary"当成"binary 的定义"，两侧各配夹具用例钉住，避免判据把 PNG 的正常邻居（woff、pdf）判红。

### 10.3 判据接上就当轮抓到同类缺陷（这条是本节存在的理由）

写完 `eol_parity` 之后第一次复跑台账，它立刻报红：

EOL-PARITY-FAIL: 1 项 ⇒ 「逐字节 / SHA256 / 字节预算」类主张在他人 clone 上不可复算

归因：`Path.write_text(...)` 走文本模式，Windows 下把 `\n` 翻成 `\r\n`
（实测 `b'a\n'` → 落盘 `b'a\r\n'`）——**一次写入就把刚归一好的文件打回原形**。
按"修一类不修一例"枚举全部落**被跟踪文本**的写盘口（临时目录样本不在列）：

| 出口 | 影响面 | 附带发现 |
|---|---|---|
| `benchmark_metrics.py` 台账 | 已实测致红 | — |
| `patch_apply.py` 补丁写盘 | **最大**：所有文档改动都经它 | 它的"写后读回复验"用 `read_text`，universal newlines 把 CR 读成 `\n` ⇒ **复验步骤自己正好掩盖该缺陷**；写与读同时改按字节 |
| `demo_video_pipeline.py` | `timeline.json` / `subtitle.ass` 两文件均已入库 | — |

`patch_apply --selftest` 由六类改**八类**（⑦LF 输入打完仍 LF / ⑧CRLF 输入被归一），
README 同步；反向证明非恒真：同平台 `write_text` 实测产出 `b'a\r\nb\r\n'`。

### 10.4 电池入口：一个静默 fail-open（本轮撞上才发现）

`run_all_suites.py` 没有 `--help`，未知参数被**静默忽略** ⇒ 我打 `--help` 想看选项，
结果它把 43 条套件从头跑到尾。同一机制更坏的形态：`--onl selftest`（打错字）也会跑成全量，

`--slice 99 120` 越界（Python 切片会静默截成空集，"这段没跑"会被读成"这段全绿"）一律 rc=2，补 `-h/--help`。

## 14. r40 增补 · 性能表现这一维：从"未实测"变成有数、有预算、有边界声明
